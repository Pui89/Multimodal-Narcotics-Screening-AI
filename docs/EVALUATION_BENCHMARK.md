# Reproducible Evaluation Benchmark

## Purpose

Define how the Multimodal Narcotics Screening AI application should be evaluated before any accuracy, robustness, or deployment claims are made. This file is a benchmark plan, not a report of achieved results.

## Evaluation tracks

| Track | Suggested metrics | Required breakdowns |
|---|---|---|
| Perception | precision, recall, F1, PR-AUC; mAP/IoU if applicable | scene, lighting, sensor, object scale |
| Open-set / UNKNOWN | unknown recall, false-accept rate, abstention rate | novel classes, out-of-distribution scenes |
| Calibration | Brier score, negative log-likelihood, expected calibration error | confidence bins, modality availability |
| Multimodal fusion | performance versus single-modality baselines | modality ablations, contradictory evidence |
| Sensor robustness | performance degradation and recovery rate | missing, stale, noisy, occluded, misaligned inputs |
| Temporal reasoning | track continuity, IDF1/HOTA where applicable | occlusion, timestamp skew, dropped frames |
| Runtime | end-to-end latency, throughput, peak RAM/VRAM, CPU/GPU use | hardware, input resolution, batch size |
| Human review | review rate, disagreement rate, time to disposition | ambiguity level, reviewer group |
| Safety invariants | unauthorized-action count; expected abstention under invalid input | malformed, degraded, unknown and contradictory cases |

Choose metrics that match the actual implemented task and data. Do not report metrics for model components that are not implemented or evaluated.

## Dataset protocol

- Document lawful data provenance, permissions, licenses, retention rules, and access controls.
- Publish the annotation guide and define label uncertainty and disagreement handling.
- Split by source event/site/time or other meaningful independent unit to reduce leakage.
- Freeze test labels and avoid tuning thresholds on the test set.
- Record class imbalance, missing modalities, exclusions, and known dataset limitations.
- Use only the minimum personal data necessary; avoid demographic or unrelated person identification.

## Reproducibility record

For every run, preserve:

- Git commit SHA and dirty/clean working-tree state;
- dataset version and split manifest checksum;
- model/checkpoint and configuration versions;
- dependency lockfile, Python/runtime and accelerator versions;
- hardware, input resolution, seeds and preprocessing;
- per-class metrics, confusion matrix, calibration and abstention results;
- failure cases, confidence intervals where appropriate, and command used to reproduce the run.

## Release gates

1. Unit tests and schema checks pass.
2. Baselines and ablation experiments are reproducible.
3. Calibration and open-set behavior are reported, including failure cases.
4. Missing, stale, contradictory and out-of-distribution input tests verify safe abstention.
5. Human-review and audit-record behavior are checked.
6. A separate safety and privacy review is completed before any real-world pilot.

## Reporting rule

No benchmark number is claimed by this plan. Report only values generated by repeatable runs on a documented dataset and configuration. Synthetic demos, SVG animations, model confidence scores, and successful unit tests are not substitutes for real evaluation. Screening output is a hypothesis for authorized human review, not proof of chemical identity or a basis for automated enforcement.
